# Малыш

Дневник роста малыша: сон, вес и рост, вехи развития, статистика.

Приложение работает **офлайн**. Все записи сначала попадают в локальную базу
браузера (IndexedDB) и только потом уезжают в Supabase. Ночью в детской с
плохим Wi-Fi таймер сна запускается мгновенно — сеть на это никак не влияет.

---

## Быстрый старт

```bash
npm install
npm run dev
```

Откроется на <http://localhost:5173>. Без настроенного Supabase приложение
полностью рабочее — просто данные живут только на этом устройстве.

## Синхронизация между телефонами (Supabase)

Бесплатного тарифа хватает с большим запасом.

### 1. Создать проект

Зайти на [supabase.com](https://supabase.com), создать новый проект.
Регион лучше выбрать поближе.

### 2. Применить схему

Supabase → **SQL Editor** → **New query** → вставить целиком содержимое
[`supabase/schema.sql`](supabase/schema.sql) → **Run**.

Скрипт создаёт таблицы, индексы и политики доступа. Его безопасно
запускать повторно — например, после обновления схемы.

### 3. Прописать ключи

```bash
cp .env.example .env.local
```

Значения взять в Supabase → **Project Settings** → **API**:

| Переменная | Что подставить |
| --- | --- |
| `VITE_SUPABASE_URL` | Project URL |
| `VITE_SUPABASE_ANON_KEY` | `anon` `public` key |

`anon key` — публичный ключ, его не страшно держать в приложении: доступ к
данным ограничен политиками RLS из схемы. Файл `.env.local` в git не
попадает.

Перезапустить `npm run dev`.

### 4. Включить вход через Google

Приложение открывается экраном входа: профиль малыша заводится уже внутри
аккаунта, чтобы записи сразу принадлежали семье.

**Google Cloud Console** → [console.cloud.google.com](https://console.cloud.google.com):

1. Создать проект (или взять существующий)
2. **APIs & Services** → **OAuth consent screen** → тип **External**,
   заполнить название и почту поддержки. Пока приложение в режиме Testing,
   добавьте себя и жену в **Test users** — иначе Google не пустит
3. **APIs & Services** → **Credentials** → **Create credentials** →
   **OAuth client ID** → тип **Web application**
4. В **Authorized redirect URIs** вставить адрес, который Supabase показывает
   в Authentication → Providers → Google. Он выглядит так:

   ```
   https://<ваш-проект>.supabase.co/auth/v1/callback
   ```

**Supabase** → **Authentication** → **Providers** → **Google**:

5. Включить провайдер, вставить **Client ID** и **Client Secret** из шага 3

> Client Secret вставляется именно здесь, а не в `.env`. Всё, что в этом
> проекте начинается с `VITE_`, попадает в собранный файл и уезжает в браузер
> к каждому, кто открыл страницу — секрет утёк бы сразу.

**Supabase** → **Authentication** → **URL Configuration**:

6. В **Redirect URLs** добавить адреса, откуда открываете приложение:

   ```
   http://localhost:5173/**
   https://ваш-боевой-адрес/**
   ```

   Без этого Supabase откажется возвращать пользователя обратно.

### 5. Настроить письмо с кодом

Вход сделан по одноразовому коду из письма — так удобнее в приложении на
телефоне, чем по ссылке, которая выкидывает в браузер.

Supabase → **Authentication** → **Emails** → шаблон **Magic Link** →
добавить в текст письма строку:

```
Код для входа: {{ .Token }}
```

Без этой правки в письме будет только ссылка, и поле «Код из письма» в
настройках окажется бесполезным.

Вход по коду из письма оставлен как запасной вариант — на случай, если
Google почему-то недоступен.

### 6. Войти

Открыть приложение и нажать **Войти через Google**. При первом входе
автоматически создаётся «семья».

### Общий доступ для второго родителя

В настройках появится **код приглашения** (шесть символов). На втором
телефоне: войти со своей почтой → в поле «Присоединиться к семье» ввести этот
код. После этого оба видят одни и те же записи.

## Установка на телефон

Приложение — PWA, в App Store его публиковать не нужно.

**iPhone:** открыть сайт в Safari → «Поделиться» → «На экран «Домой»».
Запустится в полноэкранном режиме, с иконкой, без адресной строки.

**Android:** Chrome сам предложит «Установить приложение».

Для этого приложение должно быть собрано и выложено на любой хостинг
статики (Netlify, Vercel, GitHub Pages, Cloudflare Pages):

```bash
npm run build      # результат в dist/
```

Пути в сборке относительные, а маршруты работают через `#`, поэтому
специальных настроек перезаписи путей на хостинге не требуется.

## Резервная копия

Настройки → **Резервная копия** → «Выгрузить файл». Получится JSON со всеми
записями. Загрузка обратно не затирает более свежие данные — сравниваются
времена изменения, так что файл можно применять поверх текущих.

Стоит делать раз в пару месяцев: браузер может очистить своё хранилище.

## Структура

```
src/
  data/          модель данных, локальная база, синхронизация
    types.ts       сущности: ребёнок, сон, измерения, вехи, кормления
    db.ts          IndexedDB
    repo.ts        чтение/запись + оповещение интерфейса
    sync.ts        обмен с Supabase
    hooks.ts       реактивные хуки над базой
    settings.ts    локальные настройки (тема, время сна)
  features/
    children/      профиль малыша, первый запуск
    sleep/         таймер, история, итоги
    sync/          экран входа, настройки синхронизации
  components/ui/   кнопки, карточки, шторки, поля
  pages/           экраны разделов
  lib/             время, разбор чисел, резервная копия
supabase/
  schema.sql       схема базы, политики доступа
```

### Как устроена синхронизация

У каждой записи есть `updated_at` (ставит устройство) и `synced_at` (ставит
сервер).

- **Отправка.** Всё, что помечено локальным флагом `_dirty`, уходит на сервер
  через `upsert`.
- **Загрузка.** Забираем всё, у чего `synced_at` больше сохранённого курсора.
- **Конфликты.** Побеждает запись с более поздним `updated_at`.
- **Удаление.** Мягкое — запись помечается `deleted`, иначе удаление никогда
  не доехало бы до второго телефона.

Разделение `updated_at` и `synced_at` не случайно: часы на телефоне могут
отставать, и если бы курсор считался по клиентскому времени, часть записей
проскакивала бы мимо.
